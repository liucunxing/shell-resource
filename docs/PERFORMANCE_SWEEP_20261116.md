## 本轮保留的性能修改

- 人员批量导入：复用已锁定的用户计算 revision，一次查询被导入用户的项目归属；统一 flush 后生成带真实 ID 的审计记录。保留负责人覆盖检查、权限、事务回滚及预览零写入。
- 修改项目：批量取得受影响部门的工作流状态，替代逐项目查状态；解除部门确认仍覆盖原/新部门全部项目，保留提交快照。
- 原因配置校验：只从历史提交 JSON 中投影预留原因，避免读取全部经销商分配/历史指标大对象；保持旧快照顶层回退语义，SQL 数量不变。
- 人员 Excel 导入：保留完整权限/workspace 刷新，去除其后的重复列表刷新；刷新失败明确显示“已导入但刷新失败”。

相同 PostgreSQL 连接与合成场景（23 个项目 × 300 家、30 人；23 名用户各有项目），每项使用新 Session。SQL 计数含 SAVEPOINT/ROLLBACK 控制语句；查询数回归另确认 1 人和 23 人均为 3 条 SELECT。

| 操作 | 基线秒 | 本轮秒 | SQL 原→现 |
|---|---:|---:|---:|
| 导入 23 名已分配项目的人员 | 2.968 | 0.419 | 75→6 |
| 修改项目，重置 23 个部门同级项目状态 | 1.759 | 0.960 | 35→14 |
| 历史预留原因使用检查 | 0.344 | 0.303 | 4→4 |

原因检查主要收益是减少结果数据，不将小幅计时差认定为稳定加速。计时是本机到数据库的服务耗时，受网络/预热影响，不含登录、浏览器传输和渲染，不是线上端到端 SLA。脚本为 `backend/scripts/benchmark_admin_sweep.py`；显式指定 development 配置，随机临时 schema 内使用合成数据，最终回滚并确认 schema 不存在。未修改真实业务行。

只读 EXPLAIN 抽样：分配约 0.466ms，人员约 0.052ms，历史行约 0.541ms，全源摘要约 29.497ms，历史摘要约 8.028ms；相关访问索引已存在，未发现需要新增索引的证据。数据库未启用 pg_stat_statements，不能据此声称排除了所有历史慢 SQL。部分历史/审计抽样为空，仅可确认该样本计划。已有网络证据见上一轮记录，仍不足以把用户的等待全部归因于代理。

## V20 旧模块直接删除

删除旧右侧历史参考抽屉、Insight 和嵌入 Data Agent 的前端组件、辅助状态/方法、专属样式、接口、服务、模型生成/提示词逻辑、能力包、测试及构建引用；嵌入 SDK 中自动加载的 Data Agent 桥接也已删除。旧 `/admin/reference` 写入链路同时删除。旧孤立 AdminPage 已无当前入口，一并移除。前端本地缓存中的旧字段仅做丢弃兼容。

普通和 Portal 路由均不注册旧接口，并以 404/OpenAPI 回归约束。保留 Portal 登录、Cookie、CSRF、身份校验；保留当前组合/编辑页历史指标、经销商数据及详情下钻。历史数据库表和既有迁移不删除，Alembic 仅排除两个已退役 Insight 历史表的自动删除建议。私有 TOML 中旧配置键仅兼容解析，不能重新启用模块；新的示例配置不再列出旧键。归档需求与旧部署记录可保留历史说明，不代表当前运行功能。
