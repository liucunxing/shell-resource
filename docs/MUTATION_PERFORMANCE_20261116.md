# 2026-11-16 提交、版本与人员加载性能

## 结论与修改

上一轮 `912a9ec` 测的是工作区读取，没有验证线上保存。此次在真实 PostgreSQL 的独立临时 schema 中重现了版本复制慢的问题：23 个项目、每项 300 家经销商，原服务耗时约 9.5 秒。数据量本身不足以解释等待，逐项目查询和写入往返是已确认原因。

- 创建版本：一次读取各项目最后提交快照，按业务线复用身份目录，批量写入分配和工作流；不复制未提交工作稿、不继承提交/部门确认。
- 部门提交状态：批量读取工作流和对应提交快照；有提交记录时业务查询固定 4 条，不随项目数增加。保留版本锁和一致性检查。部门操作后去掉重复状态请求。
- 人员列表：移除读取时的全局配置写锁；列表、过滤结果、总数、导入 revision 和负责人覆盖范围来自同一条数据库语句。写入仍保留原锁、权限及导入冲突检查。
- 保存分配：批量写入经销商行，复用已查询的身份与已有行，保留新经销商 active 校验。提交编号使用聚合查询，不再拉取所有历史快照。
- 提交：已保存且本地未修改时直接提交，省去重复保存；有本地修改仍先保存，再用服务器返回的 revision 提交。提交失败、冲突和请求期间本地修改均保留处理。
- 版本更新/删除：非当前版本仅刷新版本清单；当前版本、创建后自动选中新版，以及当前版本 revision 已变化的情况仍完整刷新，避免陈旧工作流。

不新增数据库迁移，不改变权限、金额口径、版本流转规则或提交快照语义。

## PostgreSQL 对比

同一连接配置、相同合成场景：23 个项目 × 300 家经销商，共 6,900 条分配；30 个用户。每项新建 AsyncSession。基线为 `e9e04bd`，优化为本次代码。表中 SQL 包含测试事务 SAVEPOINT/ROLLBACK 等控制语句。

| 操作 | 原耗时（秒） | 优化耗时（秒） | SQL 原→优化 |
|---|---:|---:|---:|
| 部门提交状态 | 2.218 | 0.549 | 50→6 |
| 保存 300 条分配 | 2.126 | 1.875 | 35→30 |
| 提交已保存草稿 | 1.355 | 1.209 | 27→25 |
| 新建版本（复制全部项目） | 9.462 | 0.952 | 238→13 |
| 删除版本 | 0.430 | 0.394 | 8→8 |
| 加载 30 人列表的首页 | 0.493 | 0.201 | 7→3 |

删除接口本身较快，前端原先还等待全量工作区刷新；非当前版本已改为轻量清单刷新。人员列表的改进还包含不再排队等待版本创建占用的配置锁，此表无并发竞争，未量化排队收益。

未修改草稿的提交现在省掉整次保存；仍有未保存改动时，保存与提交保持两步，不能把 1.209 秒宣称为所有提交的耗时。

上述为本机到数据库的服务计时，**不包括浏览器、Portal 认证、HTTP 传输及渲染，不是线上端到端 SLA**。第一次基线复测创建为 9.888 秒、部门状态 2.431 秒，网络和连接预热会影响数值。

脚本：`backend/scripts/benchmark_mutations.py`。需显式指定忽略的 `APP_SETTINGS_FILE` 和 `APP_ENV=development`；可用 `PERF_SOURCE_ROOT` 指向另行提取的基线 src。脚本只在随机临时 schema 中创建合成数据，外层事务最终回滚，并核验 schema 消失，不读取或改写真实业务行。

## 网络与验证边界

同一公网健康接口，当前网络路径预热后约 0.75–0.88 秒，绕过代理直连约 0.58 秒。冷连接曾为 2.84 秒。这能说明网络有额外成本，但不能代表用户浏览器的实际代理路由，也不足以将本次全部慢点归因于代理。

本次性能改动单独抽出验证，保留工作目录内其他协作者的版本规则改动，未混入本次提交。后端 890 项、前端 466 项通过；真实 PG 独立事务验收 35 项通过，覆盖 ARRAY、权限、版本隔离、快照复制、确认冻结、撤回及回滚清理。Ruff/Mypy、构建及包体检查另见交付结果。
