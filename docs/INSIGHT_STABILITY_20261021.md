# Insight 综合体检与四象限稳定性修复（2026-10-21）

## 复现与修改

真实 Qwen 回放复现了两类问题：

- 综合体检的严格 JSON Schema 解码在输出中途被供应商主动中止，返回 `structured_output_aborted`，没有正常结束。原实现需要再切换协议，实测一次恢复耗时 36.86 秒。综合体检现与四象限一样使用非流式 JSON object；授权结构仍随请求给模型，后端完整校验保持不变。
- 模型把两家经销商、两组 Yield 和计划金额写进同一句“分别为”，被对象与数值绑定校验拒绝。第二次调用只修改 checks，原样保留出错 summary。修复指令现明确 overview 对应顶层 headline/summary，要求重写摘要、每家单独一行。无必显复核时为综合体检提供已绑定事实的摘要起点；有复核时仍必须展开模型生成的复核正文。

另外修正 JSON object 模式的已知生成中止不重试的问题。仅对已识别的供应商中止重试一次，保留 60 秒总期限；未知参数错误、超时、重复失败仍返回失败并保留旧记录。不会拼接残缺输出、放宽事实校验或用模板冒充成功结果。

能力包版本为 `0.3.3-engineering`。不涉及数据库迁移、权限变更、预算或业务提示词修改。

## 验证

- 后端与能力包全部 320 项离线回归通过。覆盖 JSON object 中止恢复/连续失败、错误保留旧记录、完整结构和必显复核约束、摘要修复定位、日志校验阶段及敏感值不泄露。
- 使用 liucxs 已授权范围的冻结数据快照和真实 qwen3.8-flash：2 次捕获失败候选的修复通过，8 次自然生成通过（综合体检/四象限各 4 次）。总计 10 次通过，耗时 10.081–19.008 秒。修复场景首个候选来自捕获记录，第二次才调用真实模型；自然生成均调用真实模型。这组结果用内存仓储隔离，不是生产保存验收。
- 原始请求、候选和结果仅保存在忽略目录 `output/insight-stability-20261021-182134/`，不提交授权业务数据。
- 300 家合成数据使用真实模型、实际 API 服务与隔离 SQLite，验收结果见本节后续记录；不写业务数据库。

## 日志与发布边界

响应头 `X-Insight-Request-ID` 可关联应用日志与供应商 request_id。新增 `insight.request_compiled` 记录能力包版本、协议、事实/提示词/结构哈希；`insight.validation_failed` 增加 structure、fact_tokens、raw_facts、display_facts 阶段，帮助定位是结构、原始事实还是展示转换失败。旧有模型诊断仍包含结束原因、响应字节数、重试次数、执行阶段和耗时。新日志不记录完整模型输入、业务数据或密钥。

此前线上三次失败没有取得服务器日志，不能断言其内部原因与这次本地复现完全相同。本轮后期本机直连 PostgreSQL 出现 DNS/连接超时，实时数据库回放未通过；与真实 Qwen 的快照回放分别记录。SSH 仍不可用，本报告不代表修复已经部署或线上稳定性验收完成。发布后需要用 liucxs 再做线上生成和保存读回。
